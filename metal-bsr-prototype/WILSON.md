# Standalone Wilson operator and BiCGStab

This extends the existing prototype with an actual nearest-neighbor Wilson
operator, a nonsymmetric complex solver, and 96–192 RHS measurements. See
[WILSON_RESULTS.md](WILSON_RESULTS.md) for runtime and convergence. No files in
the Chroma, QDP, or SuperbBLAS checkouts are modified or linked.

## Relationship to the inspected Chroma source

The local `UnprecWilsonLinOp` in
`/Users/admin/Downloads/chroma.devel/lib/actions/ferm/linop/unprec_wilson_linop_w.cc`
sets the isotropic diagonal to `4 + Mass` and applies `-0.5 * Dslash`.
`mgproton.cc:1219` offers BiCGStab for a general operator. The comment near
`superb_contractions.h:8484` describes the Wilson off-site color/spin block as
the sum of two Kronecker terms: color × spin identity and color × gamma.

The prototype follows that normalization and decomposition. In an explicitly
defined Euclidean spin basis, it applies

```text
D psi(x) = (m+4) psi(x)
  - 1/2 sum_mu [ U_mu(x) (I-gamma_mu) psi(x+mu)
                 + U_mu(x-mu)^H (I+gamma_mu) psi(x-mu) ].
```

Color and spin factors commute. The backward link is the adjoint of the forward
link at the backward neighbor, not the adjoint of the forward link at x.
All spatial boundaries are periodic; time is antiperiodic by default. Both
directions crossing a time boundary acquire a minus sign. `--periodic-time`
removes that sign.

The spin matrices are Hermitian and obey the Euclidean Clifford algebra. With
Pauli matrices sigma_1, sigma_2, sigma_3:

```text
gamma_k = [ 0          -i sigma_k ]     k = 1,2,3
          [ i sigma_k   0         ]
gamma_4 = [ 0 I ]
          [ I 0 ]
gamma5  = diag(1,1,-1,-1).
```

This basis is documented rather than assumed to match every QDP configuration's
array ordering. No Chroma executable was used to cross-check spin components.
The product satisfies `D^H = gamma5 D gamma5`; D itself is generally non-Hermitian
and is not an SPD operator. Ordinary CG on D would therefore be unsuitable.

## Gauge data, precision and sparse representation

Each link is a seeded site-dependent SU(3) matrix generated by products of three
embedded SU(2) rotations and a determinant-one diagonal phase. Angles are sampled
within `±gauge-strength` radians. The default strength is 0.25. Forward links
differ from site to site and direction to direction. These are synthetic test
links, not gauge configurations sampled from a lattice-QCD action.

The benchmark tests positive bare masses 0.1 and 0.5. In the hopping-parameter
normalization, `kappa = 1 / (2*(m+4))`; the two masses correspond to approximately
0.12195 and 0.11111. This does not model the tuned critical mass of an interacting
production ensemble. The CLI currently accepts only positive mass.

The authoritative coefficients, RHS, accumulated solution, and true residuals
are double precision. FP32 matrix coefficients are separately rounded from those
original values. Each RHS has a different seeded double-precision known solution;
`b = D64 * x_known` is generated before timing. Self-tests include a zero RHS.

The sparse representation stores one diagonal plus two Kronecker terms for each
of eight hopping directions: **17 terms per site**, but only nine geometric
neighbors. Each gamma matrix is a spin permutation with complex unit phases, so
the existing 3×3-color / four-spin Metal kernel can apply the exact Wilson
projectors as the sum of their identity and gamma terms. CPU and GPU use the
same representation. This is not a tuned half-spinor Dslash kernel: it duplicates
color data between the two terms and performs avoidable work on diagonal blocks.
Thus the timings describe this generic prototype, not the limit of either CPU
or Apple GPU Wilson performance.

## Solver and mixed precision

All three paths use **complex BiCGStab directly on D**:

* `cpu_fp64`: eight-worker ARM NEON FP64 operator applications and FP64 complex
  recurrences, targeting 1e-10, followed by a full true-residual check.
* `cpu_mixed`: eight-worker ARM NEON FP32 corrections, accumulated into FP64,
  with CPU FP64 true-residual checks between corrections.
* `metal_mixed`: the same refinement algorithm, with FP32 BiCGStab on Metal and
  FP64 accumulation/checks on the CPU.

Mixed corrections target a recursive relative residual of 0.002. The outer loop
accepts a solution only when **every RHS** satisfies `||b-D64*x64|| / ||b|| <= 1e-10`.
Zero RHS use an absolute residual check. Converged RHS are masked/locked.
Known-solution error is checked independently after each solve.

The implementation uses complex conjugate inner products, complex alpha/beta/
omega, a fixed shadow residual within each correction, and the usual early-s
stopping check before the second operator application. Complex division uses a
scaled formula so small residuals do not underflow a naively squared denominator.
BiCGStab breakdown, nonfinite norms, exceeding 512 inner iterations or 12 outer
corrections, and missing the final true tolerance cause failure rather than a
successful benchmark row. There is no silent fallback to a different solver.

No normal equations are formed. CG, CGNE, and CGNR are not used for Wilson. There
is no clover term, even/odd Schur complement, multigrid, or other preconditioner.
The CPU-only paths perform no GPU numerical work during their timed solves.

## RHS batching and GPU execution

This is batched independent BiCGStab, not block BiCGStab. Each RHS has its own
complex scalars, convergence mask, and iteration count. It does not share a Krylov
space or exploit linear dependence between RHS. Ample RHS can amortize control
overhead and fill the GPU, but the useful criterion is **milliseconds per RHS**,
not whether a larger batch takes less wall time overall.

All inner vectors, complex reductions, scalar updates and masks stay in shared
Metal buffers. By default, four BiCGStab iterations are encoded per command
buffer with barriers between dependent dispatches. The CPU inspects convergence
flags after completion of each chunk. The GPU schedules two Wilson applications
per iteration even when an early-s stopping decision would let a CPU avoid the
second; it also executes padded iterations to the chunk boundary. These costs
are included in the reported total and visible in dispatched iteration counts.
The CPU stops as soon as the whole batch converges. Reduction order differs
between CPU and GPU, so BiCGStab counts need not match exactly.

## Reproduction

From this directory, with Xcode build tools and GPU access:

```sh
make
make wilson-test
make wilson-bench
python3 wilson_summary.py results/wilson.csv --output WILSON_RESULTS.md
```

The default benchmark is:

```sh
./build/metal_wilson --sizes 8 --rhs 96,192 --mass 0.1,0.5 \
  --gauge-strength 0.25 --samples 3 --threads 8 --chunk 4 \
  --tol 1e-10 --inner-tol 0.002 --csv results/wilson.csv
```

A short solve run:

```sh
./build/metal_wilson --sizes 3 --rhs 3,7 --mass 0.25 --samples 1 \
  --csv results/wilson-quick.csv
```

`--gauge-strength 0` selects free-field links; `--periodic-time` selects periodic
time. The executable must run from this directory so it can find the shaders.
As with the previous tests, an automation sandbox may hide Metal devices. The
working-set guard limits a case to 18 million complex vector elements because
several FP32 and FP64 vectors are resident simultaneously.

## Timing and validation

Warm solve time includes zeroing/reset, input casts, both operator applications
per BiCGStab iteration where used, all complex reductions/vector updates, Metal
encoding/submission/waits, FP64 correction updates, and **full CPU FP64 true
residuals**. Initial allocation, matrix upload, pipeline compilation, problem
generation and fixed RHS norms are outside warm time and separately identified.
The final known-solution check is outside timing; true-residual checks are inside.
Every timed solve restarts from zero with the same RHS data. There is a complete
warmup for each backend, three measured trials, and rotating backend order.

The self-test independently checks:

* Euclidean gamma anticommutation and Hermiticity.
* Every SU(3) link's unitarity and determinant.
* Entrywise gamma5 Hermiticity of the assembled small matrix, including boundary
  terms and duplicate neighbors; the random-link case must be non-Hermitian.
* A direct four-spin Wilson formula versus the 17-term FP64 CPU product.
* Metal output versus the direct FP64 Wilson formula at every component.
* The free-field Fourier symbol
  `m + sum(1-cos p_mu) + i sum(gamma_mu sin p_mu)`, including antiperiodic time.
* Complete solves on nine small random-link systems with odd RHS and zero RHS,
  full FP64 true residuals, and known-solution comparisons.

Raw per-trial timings are in `results/wilson.csv`; its `.trace.csv` companion
contains convergence after every correction. CSV setup columns expose one-time
costs. The code is in `wilson.mm` (operator/validation/driver), `bicgstab.hpp`
(CPU/GPU scheduling), and `bicgstab.metal` (GPU complex recurrences/reductions).
The original SPD benchmark shares the FP64 refinement machinery through
`solve_common.hpp` and remains independently runnable.

Wilson construction and validation now live in `wilson_common.hpp`, shared by
the original driver and the [even/odd extension](EVENODD.md). The original
unpreconditioned benchmark remains available as `build/metal_wilson`.
